# 飛翔球館小程序 · 技術方案書（SDD 第 4 步）

2026-11-04

前三步寫清楚了「做什麼」，本文件寫「用什麼做、怎麼搭」；依據是《立項書》《需求規格書》《澄清清單》。

## 總體架構

```
┌──────────┐      ┌───────────── 微信雲開發 ─────────────┐      ┌──────────────┐
│  小程序   │ ←──→ │ 雲函數：所有計算和規則                  │ ←──→ │  微信支付     │
│ 客人端+   │      │ （防重複賣、5 分鐘計時、退款、定時對帳）  │      │ 付款/查單/退款 │
│ 管理端    │      │                                       │      └──────────────┘
│ 只負責顯示 │      │ 雲數據庫：訂單、價格、商品、員工、記錄   │      ┌──────────────┐
└──────────┘      │ 雲存儲：商品圖片、橫幅圖片              │ ───→ │ 企業微信群機器人 │
                  └───────────────────────────────────────┘      └──────────────┘
```

手機上的小程序只負責顯示和讓人操作；判斷能不能訂、算價格、計時、退款這些規則，全部放在雲函數裡由伺服器執行，客人改不了也繞不過。這正是避免上一版各種 bug 的關鍵。

| 工具 | 用來做什麼 | 費用 |
| --- | --- | --- |
| 微信小程序 | 客人端和管理端的畫面 | 註冊免費；企業認證按微信規定收費 |
| 微信雲開發 | 雲函數、雲數據庫、雲存儲、定時任務，不用自己買伺服器 | 按月付費的套餐，開通時按實際價格選；2026 年可申請 6 個月免費個人版 |
| 微信支付 | 付款、查單、退款 | 按交易收手續費，以商戶後台費率為準 |
| 企業微信群機器人 | 把新訂單、退款消息發到老闆和員工的群 | 免費 |

## 雲函數分工

| 雲函數 | 負責 |
| --- | --- |
| user | 登入、協議、手機號、頭像暱稱、註銷 |
| staff | 老闆碼、員工邀請碼、員工管理 |
| booking | 客人端全部操作 |
| admin | 管理端全部操作（權限在函數內判斷） |
| payNotify | 微信支付結果通知 |
| timer | 每分鐘定時任務：到期關單、對帳、場地已使用、活動過期退款；每天刪除過期手機號 |
| initdb | 初始化數據庫 |

`_shared/` 是 booking、admin、timer、payNotify 共用的代碼（訂單核心邏輯、價格計算、微信支付封裝），由 `scripts/sync-shared.js` 複製到各函數的 `lib/`。付款、查單、關單、退款都用微信雲開發的 `cloud.cloudPay`。設定了商戶號 `MCH_ID` 才走真實支付；只有明確設定 `PAY_MODE=mock` 才會進入「模擬支付」（測試用）；兩者都沒設定時一律報錯「支付未配置」，不會悄悄進入模擬模式。**優先順序：只要填了 `MCH_ID`，不論 `PAY_MODE` 填什麼都走真實支付**；要切回模擬支付，必須同時刪除 `MCH_ID` 並設定 `PAY_MODE=mock`（澄清 H9）。

## 資料怎麼存

雲數據庫裡的每張「表」就像一本帳簿，各記一類東西。所有金額一律以「分」記（¥65.00 記為 6500），所有時間一律記北京時間。

| 表（集合名） | 記什麼 | 說明 |
| --- | --- | --- |
| 用戶 users | 微信身份、手機號、頭像暱稱、角色（客人／員工／組局員 host／老闆）、備註名、最後訂場時間、球局性別 gender（M／F，澄清 N7） | 角色決定看不看得到管理入口；註銷後只留身份和訂單關聯 |
| 場地佔用 slot_locks | 每一格「日期 + 場地 + 時段」被誰佔著：待支付、已訂、鎖場、球局（status `game`，記 gameId） | 每一格只能有一條記錄，這是防止重複賣出的關鍵 |
| 訂單 orders | 訂單號、客人、狀態、總金額、建立時間、到期時間、微信付款時間、已退款次數 | 一張訂單可同時有場地和商品 |
| 訂單卡片 order_items | 每格場地、每種商品各一條：單價、數量、已核銷／已退款／已過期張數、已退金額、券碼 | 退款、核銷都在卡片層面操作 |
| 商品 products | 名稱、圖片、價格、庫存、類型、活動日期和開始時間、上架狀態 | 已售出的商品也可以刪除；已購券不依賴商品記錄（澄清 L4） |
| 價格 prices | 常用價格（平日／周末，含生效日期）；單日價格（日期、時段、場地、價格） | 算價時先查單日價格，沒有再用常用價格 |
| 營業時間 business_hours | 日常營業時間（含生效日期）；特殊日期（時段或全天休息） | 日期條和格子都按它算 |
| 橫幅 banners | 圖片、跳轉目標、顯示方式、排序 | |
| 退款記錄 refunds | 金額、原因、操作人、微信退款單號、狀態 | 包括客人自退、管理端退、系統自動退 |
| 操作記錄 audit_logs | 查看電話、鎖場解鎖、核銷撤銷、改價等：誰、何時、做了什麼 | 只增不改，用來查責任 |
| 邀請碼 invites | 員工碼和老闆碼：碼、類型、到期時間、是否已用 | 一次性，用完或過期即失效；記錄 _id 即邀請碼 |
| 設定 settings | `owner` 記錄：目前老闆 ownerId、備用路登記的老闆手機號 presetPhone | 開發者在控制台修改 presetPhone |
| 核銷記錄 verify_logs | 核銷和撤銷：商品、張數、客人、操作人、時間、日期 | 撤銷時另加一條「撤銷」記錄 |
| 通知 notices | 新訂單、退款等通知 | 用來計算管理端紅點；同時推送到企業微信群 |
| 待支付名額 user_pending | 每位客人一條：目前那張待支付訂單的編號 | 保證同一客人同時只有一張待支付訂單（兩次結算同時到達也一樣） |
| 券碼登記 coupon_codes | 每個 6 位券碼一條：屬於哪張卡片 | 保證券碼不重複；核銷時用券碼直接找到卡片 |
| 球局 games | 標題、封面、標籤、說明、日期、鎖的格子 cells、開始／結束時間、男女價格、各種上限、最少人數、狀態（open／cancelled）、發起人、瀏覽數、**名單 roster** | 名單直接存在球局記錄裡（見關鍵機制 10），報名、退出、補位都在一個事務裡改同一條記錄 |

## 關鍵機制

上一版的 bug 大多出在這幾件事上，這次每一件都有明確做法。

**1. 防止重複賣出（項目原則 1）**

- 「場地佔用」表裡，每一格（例如「11月11日 · 5號場 · 19:00」）只允許有一條記錄，就像一個車位只有一塊車位牌
- 按「去结算」時，雲函數一次性為訂單裡所有格子申請車位牌：只要有一格已被佔，**整單全部不成立**，一格都不鎖，然後提示客人哪幾格沒了
- 兩部手機同一瞬間搶同一格，數據庫只會讓其中一個成功
- 同一個「事務」裡同時完成：佔用待支付名額、申請所有車位牌、扣庫存、登記券碼、建立訂單；卡片價格取自同一次報價，訂單總額 = 卡片金額相加；結算瞬間商品被改價則整單不成立，提示「价格已变动」
- 只接受 1–10 號場地、整點時段、正整數數量；一張訂單最多 40 項

- 訂單號不覆蓋：建訂單的事務裡先確認訂單號沒有記錄，撞號整張換新號（澄清 K1）
- 日期鎖 `locks/day_日期`：下單在事務裡確認該日「營業時間版本」沒變並改寫此鎖；改營業時間在事務裡改寫受影響日期的鎖、版本加一，「先存新設定 → 再查訂單 → 有衝突就還原」（澄清 K2）
- 價格鎖 `locks/prices`、橫幅鎖 `locks/banners`：先記版本、檢查完在事務裡確認版本沒變再保存並加一（澄清 K6、K10）
- 商品刪除在事務裡進行，與下單互斥（刪除先完成，同時結算的訂單整單失敗；購買先完成，刪除照常成功）；有人買過也可以刪除。已購券自帶名稱、價格、活動日期，核銷、退款、過期自動退款都不依賴商品記錄；退款時商品已刪除就跳過「加回庫存」。商品圖片不隨刪除移除（澄清 K5、L4）

**2. 5 分鐘到期判斷**

- 訂單建立時寫入「到期時間」= 建立時間 + 5 分鐘
- 判斷一格是否被佔，看的是到期時間有沒有過，而**不是**等定時任務來清理，所以一過期格子就能被別人選
- 別人要搶一個剛過期的格子時，雲函數先向微信查單並關單，確認原訂單沒付款，才把格子交給新客人
- 定時任務每分鐘掃一次，把已過期的訂單正式標為「已關閉」並做對帳

**3. 付款結果確認**

- 是否付款、付了多少，一律以雲函數**主動向微信查單**的結果為準；微信發來的付款通知只用來知道「哪張訂單」，偽造通知改變不了任何東西
- 付款成立的條件：微信付款時間 ≤ 到期時間，**而且**這張訂單的車位牌都還在它名下；否則（逾期付款、訂單已取消／關閉、場地已轉給別人）一律全額退款，絕不復活已關閉的訂單
- 付款成立、關單、取消都在事務裡重新讀取訂單最新狀態再轉換，兩件事同時發生只有一件生效；釋放場地只刪「仍屬於本訂單」的車位牌
- 三個來源互相兜底：微信主動發來的付款通知、到期時主動查單、定時對帳

**4. 退款不會退錯、不會退兩次**

- 退款分三步：① 事務裡「預留」——固定退款單號（訂單號 + R + 退款流水號）、卡片標記退款中、退款次數 +1、寫入退款記錄（處理中）；② 向微信申請；③ 微信受理後在事務裡結算（已退金額、張數、放出場地、退回庫存），重複執行也只生效一次
- **退款流水號 `refundSeq` 只增不減**，專門產生退款單號；**退款次數 `refundCount`** 用來控制微信每單 50 次上限，微信明確拒絕時可以還回去。兩者分開，已發出的單號永遠不會被別的退款重用；新退款寫入前確認該單號沒有記錄，絕不覆蓋。舊訂單沒有流水號時，從已有退款記錄的最大編號接著編（澄清 H1）
- 微信回覆丟失（結果不明）時保留預留，定時任務用**同一個**退款單號重試，微信保證同一單號只退一次；每次不明記下下次重試時間（1、2、4、8 分鐘遞增，最長 10 分鐘），未到時間的不佔每輪名額，每輪先處理沒試過的、再按重試時間最早的輪流（澄清 H2）；微信明確拒絕時撤銷預留並通知管理端人工處理
- 微信已受理、本地記帳失敗：同樣標為結果不明並排下次重試時間，用原單號重試，不撤銷預留、不換單號；定時任務處理每筆退款前先記下它的下次重試時間，任何一步出錯都不會讓它一直佔住每輪名額（澄清 I3）
- 退款前檢查：本次金額 ≤ 卡片剩餘可退金額；同一卡片同時只允許一個退款在進行；退款中的張數不能核銷，核銷和退款在事務裡互斥
- 核銷前檢查：訂單已付款、券未過期（固定日期活動過了活動日即過期）、張數足夠
- 核銷：扣券和核銷記錄在**同一個事務**寫入；核銷記錄的編號 = 前端每次按「确认核销」產生的操作編號，同一編號重試直接返回原結果、不重複扣券；之後更新訂單狀態失敗不影響回覆。撤銷核銷同理（澄清 I1）
- 退款中的顯示：卡片按張數顯示「退款中 N」，訂單狀態加「退款处理中」；退款成功才顯示已退款（澄清 I2）
- 晚到的錯誤回覆只能把「處理中」改成「結果不明」，不能把已完成的退款改回去；結算時只把仍標記「本退款處理中」的卡片金額記入訂單，同一筆退款重複結算也只記一次帳
- 微信「受理」退款即記帳；定時任務再用退款查詢確認最終到帳，退款關閉或異常時通知管理端人工處理

- 固定日期活動過期自動退款：查詢時就排除退款中、失敗後 1 小時冷卻中的券；先處理沒失敗過的，再按失敗最早的輪流（澄清 H3）
- 報表的退款按微信受理、系統記帳的時間 `doneAt` 歸到哪一天（澄清 H7）

**5. 時間和金額**

- 所有「現在幾點」都由雲函數提供，手機時間不參與任何判斷；倒計時只是把伺服器給的到期時間顯示出來
- 金額全程以「分」計算，只在畫面上顯示時統一轉成 ¥88.50 格式，全小程序只有一個轉換的地方

- 底部結算欄元件 `components/cart-bar`（澄清 M3）：讀手機緩存的購物車，呼叫 `booking.quote` 算合計（不含失效項），與購物車頁同一算法；訂場、活動兩頁共用，取代 `cart-fab`
- 分享（澄清 M4–M6）：只有訂場首頁、活動列表、活動詳情寫 `onShareAppMessage`、`onShareTimeline`，其餘頁面不寫，微信自動顯示不能轉發；活動詳情分享路徑 `/pages/product/index?id=商品編號`，帶名稱和價格供朋友圈單頁模式顯示；封面圖用雲存儲臨時連結
- 價格資料 `prices`（type regular）可帶 `slots`：`[{ startHour, endHour, weekday, weekend }]`，時段不重疊；`priceFor` 順序為單日價格 ＞ 時段價 ＞ 預設平日／周末價（澄清 L8）

- 球局（澄清 N 節）：見「關鍵機制 10」

**6. 權限**

- 時間選擇元件 `components/time-picker`：微信 `picker mode="multiSelector"` 兩列（時 00–23、分 00–59），對外仍輸出 `HH:MM` 字串；取代 `picker mode="time"`（澄清 L5、G10）
- 時間不能選過去（澄清 L6）：`bannerSave`、`productSave` 在伺服器檢查，開始時間比「現在所在的那一分鐘」早就拒絕，除非是編輯且開始時間和已存的一樣；限時橫幅結束時間必須晚於現在；訂場跳轉日期不能早於今天

- 協議同意（澄清 L1、L2）：`privacy-modal` 首次打開自動彈出；「不同意」只關閉並記在本次打開（`app.globalData.privacyDeclined`）。需要帳號的操作先呼叫 `utils/privacy.ensure(page)`：已同意直接繼續，否則彈出同意畫面，不同意返回 false 並停止該操作。同意後不再自動請求手機號

- 用戶帳號編號 = 「U」+ OpenID 雜湊，事務裡建立，同一 OpenID 只有一個帳號；老闆預設手機號綁定在同一事務裡完成比對、降級、升級、清空（澄清 K3、K4）

- 每個管理功能的雲函數，都先查「用戶表」確認操作人是老闆或員工，以及有沒有這項權限；不相信手機傳來的身份
- 組局員（role `host`）呼叫 `admin` 只允許 `me` 和球局相關操作（`HOST_ACTIONS`），且只能管 `hostId` 是自己的球局

**7. 操作後不跳回頂部（全局規則 G1）**

- 操作後只更新變動的那幾格或那幾張卡片，不重新載入整頁

**8. 資料保存期限**

- 訂單自「交易完成」起滿 3 年才匿名化（清掉手機號、微信身份、客人編號，保留金額和明細）；交易完成 = 付款、場地打完、券核銷、退款受理、活動日過去中最晚的時間；未滿 3 年的記下 `retainUntil`，到時再處理（澄清 H8）
- 管理操作日誌和通知記錄保留 1 年；客人最後一次訂場滿 1 年刪除手機號

**9. 舊數據兼容與遷移**

- `initdb` 進度存在 `settings/initdb_progress`，可續跑（澄清 K12）；新增集合 `locks`；合併重複帳號（澄清 K4）
- 依賴套件版本寫死：wx-server-sdk 3.0.4、xlsx 0.18.5、qrcode 1.5.4（澄清 K11）

- 訂單必須有完整卡片清單 itemIds 才能做任何狀態轉換；沒有時先按訂單號查卡片補上，仍查不到就拒絕操作，絕不把「讀不到卡片」當成「已全部退款」
- `initdb` 同時是遷移工具：補 itemIds、補核銷記錄的 userId、把所有券碼登記到 coupon_codes 並處理重碼；可重複執行
- 刪除手機號時，按客人編號和訂單號兩種方式清除核銷記錄，覆蓋舊結構

**10. 球局（澄清 N 節）**

- 發起（`admin.gamePublish`）：先處理已過期的待支付佔用，再在一個事務裡確認所選格子都沒有佔用記錄、日期鎖的營業時間版本沒變，然後寫入每格 `slot_locks`（status `game`）和球局記錄；格子要在可訂日期、營業時間內、未過去、時段連續
- 名單 `roster`：`[{ userId, gender, state, orderId, itemId, at, expiresAt, nick, avatar }]`，state：`pj` 待支付佔名額、`pw` 待支付排候補、`j` 已報名、`w` 候補。待支付的 `expiresAt` 過了就不再算佔用。名額計算：已報名＋待支付佔名額，分總數和男女
- 報名（`booking.gameJoin`）：和下單同一套（待支付 5 分鐘、user_pending、微信下單），訂單卡片 kind `game`（gameId、標題、性別、價格、開始／結束時間）；事務裡讀球局，有名額記 `pj`，沒有記 `pw`
- 付款確認（`markPaid`）：球局卡片要在名單上、球局未取消、未開始才算成立；`pj` → `j`，`pw` → `w` 後執行補位；否則全額退款並把他從名單移除
- 待支付關閉（`planRelease`）：從名單移除並補位
- 退款結算（`finalizeRefund`）：球局卡片退完 → 卡片 status `refunded`，從名單移除並補位；退出、移出、取消、候補未補上都走這條
- 補位：按候補先後，第一位符合總數和性別上限的變成 `j`，重複到沒有可補的為止
- 需要系統退款的情況先在卡片記 `gameOut`（kicked／cancelled／nofill）再退款；定時任務每分鐘找「已付款、有 gameOut、沒在退款中」的卡片重試，保證最終都退到
- 定時任務：最少人數不足且距開局不到 2 小時 → 取消；開局時名單上的候補 → 記 nofill；結束時間過了的已報名卡片 → `used`；取消的球局：放回格子、全部卡片記 cancelled
- 計算訂單狀態時，球局卡片和場地一樣：退完算已退款，結束時間過了算已完成
- 改營業時間、鎖場檢查「已有訂單」時，status `game` 的格子和已訂同樣處理；管理端鎖場／解鎖不能動球局的格子
- 報表：球局報名費計入「活動收入」；場地使用率只算客人訂的場地，不含球局鎖的格子
- 名單不存頭像暱稱，顯示時讀帳號上現在的資料（客人改了、刪了、註銷了，名單跟著變）；註銷和 1 年未訂場清理時一併清掉性別
- 新集合 `games`：部署後執行 `initdb` 建立，權限同其他集合（`read: false, write: false`）

## 微信關單限制與待支付時長

查證微信支付文檔時發現：訂單生成後**最少 5 分鐘**才能調用「關閉訂單」。（來源：[微信支付 · 關閉訂單](https://pay.weixin.qq.com/wiki/doc/api_external/ch/apis/chapter3_5_7.shtml)）

**2026-11-04 決定：待支付由 60 秒延長為 5 分鐘**，正好與微信的關單限制對齊：

- 5 分鐘到期時，雲函數先查單；沒付款就向微信關單，關單成功才放出場地，之後客人無法再付款
- 三道防線照舊保留，逾期付款自動全額退款作為最後保險
- 待支付頁的「取消订单」按鈕做得醒目，客人不想要可以馬上釋放場地，不用等 5 分鐘
