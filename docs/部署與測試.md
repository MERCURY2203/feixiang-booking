# 部署與測試（全部階段）

本文件教你把整個小程序放上微信雲開發並逐項測試。照順序做，每一步做完再往下。
階段 1 的細節（老闆綁定、員工測試）見《部署與測試-階段1》。

## 一、雲函數一覽

| 雲函數 | 用途 | 需要的設定 |
| --- | --- | --- |
| `user` | 登入、同意協議、手機號、頭像暱稱、註銷 | — |
| `staff` | 老闆碼、員工邀請碼、員工管理 | 環境變量 `QR_ENV_VERSION`（上線後設為 `release`） |
| `booking` | 客人端：訂場表格、購物車、下單、付款、我的訂單、退款、活動、券碼 | 環境變量 `MCH_ID`、`WECOM_WEBHOOK`、`TPL_TIMEOUT_REFUND`、`TPL_TIMEOUT_REFUND_FIELDS` |
| `admin` | 管理端：核銷、訂單、鎖場、商品、橫幅、價格、營業時間、報表 | 同上 |
| `payNotify` | 微信支付結果通知（付款成功時由微信調用） | 同上 |
| `timer` | 定時任務：每分鐘處理到期訂單、對帳、場地已使用、活動過期退款；每天 3 點刪除過期手機號 | 同上；上傳後要「上傳觸發器」 |
| `initdb` | 初始化數據庫（只執行一次） | — |

`_shared` 資料夾**不是雲函數**，不用上傳。它是公共代碼，已複製到 `booking`、`admin`、`timer`、`payNotify` 的 `lib/` 裡。以後修改 `_shared` 裡的檔案後，要在項目根目錄執行 `node scripts/sync-shared.js`，再重新上傳這 4 個雲函數。

## 二、上傳

1. `miniprogram/config.js` 的 `CLOUD_ENV` 已填好 `cloud1-d8g2j3h1w2834f1f8`
2. 在開發者工具裡，對 `user`、`staff`、`booking`、`admin`、`payNotify`、`timer`、`initdb` **逐個**右鍵 →「上傳並部署：雲端安裝依賴」
3. 對 `timer` 再右鍵 →「上傳觸發器」（每分鐘自動執行）
4. 雲開發控制台 → 雲函數 →「版本與配置」：`timer` 的**超時時間設為 60 秒**，`booking`、`admin`、`payNotify` 設為 20 秒（默認 3 秒太短，付款和退款要和微信來回通訊）
5. `initdb` 的超時時間也設為 60 秒，然後執行 `initdb`（見《部署與測試-階段1》第三步），會建立 16 個集合並做數據遷移。看返回結果的 `migration.done`：是 `true` 才算完成，`false` 就再執行一次。全新環境第一次就會是 `true`
   - 遷移做三件事：舊訂單補上卡片清單、舊核銷記錄補上客人編號、所有券碼登記到 `coupon_codes`（如發現重複券碼，給較新的那張換新碼，換了哪些列在 `codesChanged`）
   - `ordersWithoutItems` 列出的是找不到任何卡片的訂單，這些訂單系統會拒絕取消、退款等操作，需要人工查看
   - **以後每次更新雲函數，都先上傳 `initdb` 再執行一次**，確認 `done: true` 後才讓客人使用
6. 設定數據庫和雲存儲權限（見《部署與測試-階段1》第四步）

## 三、環境變量（雲開發控制台 → 雲函數 → 選函數 →「版本與配置」→「環境變量」）

`booking`、`admin`、`payNotify`、`timer` 四個函數都要填**同樣**的值：

| 名稱 | 填什麼 | 不填會怎樣 |
| --- | --- | --- |
| `MCH_ID` | 微信支付商戶號（10 位數字） | 付款時提示「支付未配置」，不能下單 |
| `PAY_MODE` | 只在測試時填 `mock`：付款時彈出測試用的確認框，不扣真錢。**接通真實支付後必須刪除** | 不填就是正常模式 |
| `WECOM_WEBHOOK` | 企業微信群機器人的完整地址 | 不發群消息，只有管理端紅點 |
| `TPL_TIMEOUT_REFUND` | 「超时已退款」訂閱消息模板 ID | 不給客人發通知 |
| `TPL_TIMEOUT_REFUND_FIELDS` | 模板裡「說明」和「金額」兩個字段的名稱，用逗號分隔，例如 `thing1,amount2` | 默認用 `thing1,amount2` |

客人端的模板 ID 也要填到 `miniprogram/config.js` 的 `TPL_TIMEOUT_REFUND`，客人下單時才會請求授權。

### 接通真實微信支付

1. 微信支付商戶平台：商戶號關聯小程序 AppID
2. 雲開發控制台 →「設置」→「其他設置」→「微信支付配置」：添加商戶號，按提示在商戶平台確認授權（含**退款**權限）
3. 4 個函數填好 `MCH_ID`，**刪除 `PAY_MODE`**，重新上傳一次
4. 用 ¥0.01 的單日價格測試一次真實付款和退款，再改回正式價格

## 四、逐項測試

建議準備 3 個微信：老闆、員工、客人。每項打勾後在《05-任務清單》把對應任務勾上。

還沒有商戶號時，先給 `booking`、`admin`、`payNotify`、`timer` 4 個函數設環境變量 `PAY_MODE=mock` 才能測試下單（模擬支付）。

**上傳前先跑自動測試**：電腦裝好 Node.js 後，在項目根目錄執行 `node tests/run.js`，最後一行顯示「全部通過」才上傳。它用假的雲開發環境把付款、取消、退款、核銷、同時下單、舊數據遷移等 30 種情況真實跑一遍（包括 Codex 兩次檢查報告裡的 R1–R12、N1–N7）。

- [ ] 營業時間 → 特殊日期設某天「全天休息」，日期條跳過那天
- [ ] 設一條單日價格，訂場頁該格顯示新價格；價格預覽與訂場頁一致

## 五、實作備註（2026-11-04 已確認）

1. **橫幅排序**：按住每張橫幅右邊的「≡」上下拖動，放手後保存。
2. **管理端紅點**：顯示「上次打開訂單管理之後的新消息數」，打開訂單管理即清零。
3. **待支付期間客人主動取消**：微信規定下單 5 分鐘內不能關單，所以取消時**立即放出場地，別人馬上就能訂**；5 分鐘後由定時任務向微信正式關單。萬一取消的人在這幾分鐘內仍付了款，系統自動全額退款，不會出現重複賣出。
4. **編輯商品庫存**（2026-11-04 依檢查報告修正）：保存時按「打開編輯頁時的庫存 → 你填的庫存」的增減量計算。例如打開時 10、你改成 15，期間賣出 1 張，保存後是 14；不會把已賣出的庫存加回來。同一次打開的編輯頁連按保存或網絡重送，庫存只調整一次；保存失敗後想改數字，請返回重新打開編輯頁。
5. **購物車和訂單最多 40 項**：購物車滿 40 項時不能再加；一張訂單也最多 40 項（數據庫事務的操作上限）。每種商品一次最多 99 張。
6. **退款處理中**：微信回覆丟失時，畫面提示「退款处理中，稍后到账」，該卡片暫時不能再退或核銷；定時任務每分鐘用同一個退款單號補做，不會退兩次，兩個處理者同時重試也只記一次帳。微信明確拒絕（例如商戶號餘額不足）時，企業微信群收到「退款失败，请人工处理」。
   - 微信「受理」退款後，帳目即記為已退；之後定時任務用退款查詢確認是否真的到帳（處理中的每 10 分鐘查一次，最多查 30 天）。如微信返回退款關閉或退款異常（例如客人銀行卡已註銷），企業微信群收到「退款异常，请人工处理」，需在微信支付商戶平台人工處理
8. **協商部分退款**：管理端可以只退一部分金額並結束該卡片（例如客人玩了一會兒不想繼續，雙方議定只退部分款項）。結案後該卡片不能再退差額，這是預期設計。
7. **一年未訂場自動刪除**：客人的手機號、頭像、暱稱刪除，訂單和核銷記錄裡的手機號一併刪除，管理端顯示「已注销用户」。
10. **資料到期處理**（2026-11-09）：`timer` 每天凌晨 3 點除了刪除一年未訂場客人的手機號，還會：把滿 3 年的訂單匿名化（清掉手機號、微信身份、客人編號，保留金額和明細，報表不受影響）；刪除超過 1 年的管理操作日誌和通知記錄（法律要求至少保存 6 個月）。與隱私政策「信息存在哪裡，保存多久」一致。
11. **協議版本**（2026-11-09）：`config.js` 的 `PRIVACY_VERSION` 是協議版本號；協議有實質修改時改這個值，所有客人下次打開會重新看到同意畫面。客人點「同意」後，伺服器記下版本成功才放行；登入本身不建立用戶資料，同意後才建立。
12. **結算確認價格**（2026-11-09）：結算時小程序把客人確認的合計一併送出，伺服器現價不同就不下單，彈窗告知新合計，客人重新確認。
9. **訂單卡片分開顯示**（2026-11-06）：訂場和活動不同類，列表裡各自一張卡片；金額記在訂單明細（`lines[].fee`）裡，所以要重新部署 `booking`、`admin` 之後新下的訂單才會拆開；舊訂單維持一張卡片。
